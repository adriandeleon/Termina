## 1. Verdict

The hot path is sound. The conventions in AGENTS.md — dirty flag plus one `AnimationTimer`, drawing
per style run, no `runLater` per write — hold, and the profile shows it: during a 400 000-line burst
the FX thread held 17% of samples and `render` under 1%; the emulator thread held 73%, and 85–90% of
*that* is JediTerm's own buffer code. Termina's own overhead on the emulator thread is about 11%, and
two thirds of it is avoidable (§2.2). Nothing here is a bug a user would file; it is where the next
milliseconds are.

The five things worth doing, in order:

1. **Every settings write is a synchronous, file-locked disk transaction on the FX thread followed
   by a re-apply to every pane in every window** — including writes nothing visual depends on, and
   including zoom-chord auto-repeat and spinner ticks (§4.1, §4.2, from code).
2. **A frame redraws the whole visible grid under the buffer lock, and updates the scrollbar inside
   it** (§3.1, §3.2, from code). The cheap half — move `updateScrollBar()` out of the lock — is a
   two-line change.
3. **The type-ahead gate lower-cases the foreground program's name on every buffer mutation**: 3.4%
   of emulator-thread time in the burst, for a feature that is off unless `ssh` is running (§2.2,
   measured).
4. **The theme stylesheets are 165 KB and 1 073 rules each, of which the app uses a few dozen**;
   CSS parsing and the first style pass are about 30% of the FX thread's startup samples (§5.1,
   measured).
5. **Two settings-window UX defects from a stylesheet in the wrong scene**: the key-recording
   field's "Press a shortcut…" prompt is invisible exactly while recording, and the Debug Log
   window's path label is unstyled (§4.4, from code).

Then the dead code in §6, which is small and certain.

## 3. Rendering and input (from code)

### 3.1 No damage tracking: a dirty frame redraws every visible row
`TerminalView.render` (`:964-1008`) fills the canvas, walks every visible row through
`processHistoryAndScreenLines`, draws every style run, then every overlay. A cursor move, a focus
change, a hover change or a prompt-mark change sets the same single `dirty` flag and costs the same
full frame. For scrolling output that is the right thing (everything changed). For a TUI with a
ticking clock or spinner, or a cursor blinking in a 200×60 themed vim, it is 600–1 200 `fillText`
calls per frame at the program's refresh rate — an estimated 1–3 ms of FX-thread work under the lock,
plus the rasterisation. JediTerm already reports `linesChanged(row)` through the
`TextBufferChangesListener` that `HistoryFollow` implements and does not override; a dirty-row set
recorded there, with a full redraw on `layoutEpoch`, scroll, resize and palette change, is the
medium-effort version. Measure first: in the burst profile `render` was invisible, so this matters
for TUIs, not builds.

### 3.2 The frame draws, and the scrollbar updates, while holding the emulator's lock
`render` takes `buffer.lock()` at `:981` and releases at `:1007`, after `updateScrollBar()`
(`:1006`). While output streams at origin 0 the scrollbar's `max` and `value` change every frame, so
the bar skin's invalidation runs inside the lock, and the emulator thread blocks on `lock()` for the
whole frame. **Fix now:** read `history` and `scrollOrigin` into locals under the lock and call
`updateScrollBar()` after `unlock()`. **Fix later:** snapshot the visible runs under the lock into a
reused list and draw outside it.

### 3.3 `drawPromptMarks` copies the whole command list every frame
`TerminalView.java:3030` → `PromptMarks.all()` (`PromptMarks.java:86`) is `List.copyOf(commands)`
under `synchronized`, up to `MAX_COMMANDS = 2000` records, then iterates all of them to find the
failed ones. Once a shell has emitted one OSC 133 mark this runs on every dirty frame for the life
of the tab. **Fix:** keep a volatile snapshot rebuilt in the mutators, or keep the failed ones
separately.

### 3.4 A selection is re-extracted as text on every frame after any output
`dropSelectionIfRewritten` (`:2706-2718`), run from `render` whenever `selectionToVerify` was set,
which `onModelChanged` sets on every mutation while a selection exists. It rebuilds the selected
text — one `String` per selected row, up to `VERIFIED_ROWS = 1000` — under the lock, at frame rate,
for as long as output arrives. **Fix:** use `linesChanged(row)` to set the flag only when a changed
row intersects the selection.

### 3.5 Hovering a declared (OSC 8) link is O(cells × entries) per mouse move
`declaredLinkAt` (`:1854-1884`) calls `buffer.getStyleAt(x, row)` for every slot of every row of
the logical line (up to nine rows), and `getStyleAt` walks the line's entries linearly. Under the
lock, per pixel of travel while the modifier is held; the result is not reused between moves. **Fix:**
walk each row's entries once and emit spans, or short-circuit when the pointer is still inside the
last hover's spans.

### 3.6 The per-glyph fallback never re-batches
`drawGlyphs`/`drawCodePoint` (`:1138-1184`): any run containing an astral character (every Nerd Font
icon, every emoji), a `DWC` filler (any CJK) or a private-use code point goes glyph by glyph, with
`new String(Character.toChars(cp))` per glyph. An `eza` listing puts the *whole* run that holds the
icon on this path, filename included; a screen of CJK is ~6 000 `fillText` calls and allocations per
frame. **Fix:** inside the slow path, batch maximal sub-runs of one-cell BMP characters into one
`fillText` and draw only the special code points singly.

### 3.7 Smaller per-frame costs
- `drawSelection` (`:2744-2753`) reads each visible row's text twice (`slotsInRow` then again) and
  calls `onRow` for rows outside the selection. Read once; skip rows outside `[start.y, end.y]`.
- `TerminalPalette.ansi()` clones the 16-colour array per call; `drawPromptMarks`,
  `drawSearchMatches` and `drawPaneFocus` call it per frame. Add an indexed accessor.
- `drawSearchMatches` (`:3477-3478`) creates two `Color`s per frame while the find bar is open;
  derive them in `setPalette`.
- `showLinkTarget` (`:1715`) calls `requestLayout()` on every hover transition even with no status
  label; guard it.
- OSC 52 and OSC 9 post one `Platform.runLater` per sequence (`:2850`, `:2927`); the notification
  rate limit is applied *inside* the posted runnable. The bell and titles are coalesced with an
  `AtomicBoolean`; give these two the same.

### 3.8 A hidden tab with streaming output keeps the pulse at frame rate
The painter counts `onOutput.run()` as work every frame (`:356-360`) so the timer never idles while a
background tab produces output, even though `render` is correctly skipped off screen. The per-frame
cost is a no-op `TabMarkState.apply`; the cost is that JavaFX keeps pulsing at 60 fps, which is what
`FrameGate` exists to prevent. Count it as work only when it changed the mark, or deliver it through
a `PauseTransition`.

## 4. Window chrome and settings (from code)

### 4.1 Every settings write is a synchronous disk transaction on the FX thread
`Settings.put` → `putQuietly` → `save()` (`Settings.java:1016-1034`, `:255-288`): open and lock
`settings.properties.lock`, `readAllBytes` and parse the whole file, merge, `createTempFile`,
`writeString`, atomic move — then `fireChange()`. Callers that fire per tick: the font-size spinner
(`SettingsWindow.java:880-884`), padding (`:1067`), scrollback (`:1119` — a setting that cannot even
apply live), sync interval (`:2054`), the zoom chord under key auto-repeat
(`TerminalWindow.java:3283-3290`), the opacity slider via arrow keys (`:973-977`). Only the opacity
*drag* defers to drag end (done right, `:970-980`). On a local disk this is a few milliseconds per
tick; on a network home directory it is a visible stutter. **Fix:** set the property and
`fireChange()` at once, but coalesce `save()` through a short timer with a flush on `onHiding` and
`Platform.exit`; `lastSaveError()` then reports after the deferred save. `WindowManager.
maybeCheckForUpdates` → `setLastUpdateCheck` is one such transaction moments after first paint.

### 4.2 `fireChange()` has no key, so every change re-applies everything to every pane
`WindowManager.applySettingsEverywhere` (`:223-230`) resets the user-agent stylesheet (JavaFX's
`StyleManager` is believed to short-circuit an unchanged URL; unverified), applies the colour scheme
to every open window, and calls `TerminalWindow.applySettings` on every window, which per window
re-resolves every key binding and compares every menu accelerator (`:2951-2967`), churns the
`TabPane` and `MenuBar` style classes even when unchanged (`:594-608`, `:641-651`), and runs
`applySettingsTo` on every pane. `TerminalView.setPalette` (`:717-722`) and `setPreferredCursor`
(`:756-759`) do not short-circuit: every settings change restyles every pane's scrollbar (a CSS
re-application) and repaints every pane — including for `ui.language`, `updates.*`, `sync.*`,
`profiles.*`, `ui.confirmClose`, `input.confirmPaste`, none of which a pane draws. `setFontSize`,
`setFontFamily`, `setTextPadding` and `setScrollBarEnabled` already guard on equality; give the other
two the same guard (compare the theme id, or `Arrays.equals` on the palette's array), touch the style
classes only when the boolean changed, and longer term pass the changed key through `onChange`.

### 4.3 The settings window reloads itself in full on every change, including its own
`onSettingsChanged` → `reload()` whenever showing (`SettingsWindow.java:252-254`; `reloading` only
stops recursion). Each click or tick re-sets ~30 controls, `setAll`s the theme combo's items (which
clears its selection and rebuilds cells), resolves the effective key bindings **four times** and
re-parses every stored chord with `KeyCombination.valueOf` (`:1459-1475`), rebuilds the profile list
(re-firing its selection listener into `commitProfileEdit`/`showProfile`), and rebuilds the preview
with 9 new `Label`s and 16 new `Region`s (`:2272-2278`). Several controls then call `refreshPreview()`
or `refreshProfileList()` a second time after the broadcast already did (`:821-829`, `:862-866`,
`:880-884`, `:1510-1514`, `:1563-1569`), and `confirmReset` calls `reload()` after `resetToDefaults`
already fired it (`:368-369`). **Fix:** skip the reload when the change originated in this window,
or reload only the changed key's controls once §4.2 carries a key; drop the duplicate refreshes.

### 4.4 Two rules live in a stylesheet the scene that needs them does not load
- **The key-recording prompt is invisible while recording.** The field adds `shortcut-capture` and
  the prompt "Press a shortcut…", and is emptied on focus (`:1284-1301`), so the prompt is the only
  instruction. The rule that keeps a focused prompt visible, `.shortcut-capture:focused`, is in
  `app.css:454`; the settings scene loads only `settings.css` and `ui-font.css` (`:342-344`), and
  the theme sheet sets a focused prompt transparent (`editora-dark.css:4503`). Net: a blank box. Not
  driven; worth one `-Dtermina.captureSettings` with a field focused. **Fix:** move the rule to
  `settings.css`.
- **The Debug Log window's path label is unstyled.** `DebugLogWindow.java:34` uses `settings-path`,
  defined only in `settings.css:105`; that window loads `app.css`. Move or duplicate the rule.

### 4.5 A settings change from elsewhere overwrites text being typed
`reload()` sets `shellField`, `linkCommandField`, `syncRepository` and `syncBranch` unconditionally
(`:2246-2250`), and `showProfile` resets the profile name/command/directory fields (`:1690-1692`).
Key-recording fields are guarded by `isFocused()` (`:1468`); these are not. A sync run finishing, a
theme import completing, or a zoom chord in a terminal window lands mid-edit. **Fix:** skip
`setText` on a focused field, as `reloadKeys` already does.

### 4.6 Smaller
- `Themes.byId` builds a new list and four `ThemeEntry`s per call (`Themes.java:85-98`); it is
  called twice per pane, per tab in `applyWindowTheme`, and from the `Window.getWindows()` listener
  (`WindowManager.java:71-77`) *before* the popup check, so every tooltip and menu opening allocates
  a theme list. Cache the built-ins; compute the scheme lazily for non-popups only.
- First open of Settings builds all six pages and measures every installed font on the FX thread
  (`MonospaceFonts.available()`, documented at ~98 ms for 185 families). One-off per process; pre-warm
  in the background at startup if it is felt.
- `DesktopNotifier.post` spawns one process per notification on a single worker with an unbounded
  queue and a 5 s wait each (`:312-328`); a program looping OSC 9 queues minutes of `notify-send`.
  Rate-limit per tab before the queue.
- `TerminalWindow.onKeyPressed` (`:3198`) linearly tests ~60 `KeyCombination.match` per key press.
  Cheap; an index by `KeyCode` would make it constant.

## 5. Startup

### 5.1 The theme stylesheets carry a design system the app does not use
`editora-dark.css` and `editora-light.css` are 165 KB and 1 073 rules each, following the vendored
AtlantaFX structure. The app creates 19 kinds of control (`Label`, `Button`, `CheckBox`, `TextField`,
`ComboBox`, `Spinner`, `ListView`, `ContextMenu`, `SplitPane`, `ScrollPane`, `Hyperlink`,
`ToggleButton`, `TextArea`, `TabPane`, `Slider`, `MenuBar`, `Tooltip`, `Alert`, `TextInputDialog`);
the sheets also style charts, `HTMLEditor`, `DatePicker`, `ColorPicker`, `TreeTableView`,
`Pagination`, `Accordion`, `TitledPane`, `ToolBar`, `ProgressBar`, `RadioButton`, `MenuButton`,
`ChoiceBox`, `PasswordField`, `TableView` and `TreeView`. Parsing and the first style pass were about
30% of the FX thread's startup samples (§2.1); a theme switch re-parses the sheet. Pruning the unused
component sections (keeping the `.root` token block and the controls above plus the JavaFX skin
classes they pull in) would roughly halve the sheet with no visible change. Low risk if done by
section; verify with a capture of Settings, a dialog and the context menu.

### 5.2 Icons, fonts and the PTY on the FX thread
- `Icons.load` decodes eight PNGs (16–512 px) on the FX thread: 7% of startup samples. The 512 and
  256 sizes are the expensive ones and matter only to a few window managers; decode them on a
  background thread and `setAll` later, or drop 512.
- `Fonts.load` registers 20 TTFs: four faces of each of four monospace families, four of Inter, and
  the symbols font. Only the configured family, Inter and the symbols font are needed before the
  first frame; the other three families exist for the picker. Load them when Settings opens.
- `ShellLauncher.start` (the PTY spawn) is 5% on the FX thread. Inherent unless the shell starts
  before the window shows; probably not worth the complexity.
- `icon-1024.png` is bundled (`resources/com/termina/icons/`) but nothing loads it: `Icons.SIZES` stops
  at 512 and no build script names it. Delete it or use it.

## 7. Done well — do not re-raise

- Repaint coalescing: `dirty` plus one `AnimationTimer` per view; `FrameGate` stops the timer after
  ten idle frames; `wake()` is a single CAS from the emulator thread; `layoutChildren` renders in
  the layout pass so a resize never paints twice.
- Bell, titles, resize (60 ms), search refresh (≥250 ms, scaled by the last scan), search typing
  (120 ms) and `decorateHeadersLater` are all coalesced; search re-runs on a flag the painter reads,
  never per change.
- Scrollback search copies rows out of the lock in 2 000-row chunks, scans bottom-up, stops at
  `MAX_MATCHES`; matches ride on `linesScrolled`.
- Truecolour `Color`s are cached; the eight faces are built once per font change; `measureFont` is
  the only `Text` node and runs only then; `MonospaceFonts` and `IconFont` cache their scans.
- The fast path draws a whole style run with one `fillText`; `RunColumns`/`CellWidth` take a
  `CharSequence` so a run is copied once per frame.
- Mouse move with no modifier is one boolean; `reportMotion` is gated on mode 1003 and dedups by
  cell; `Files.exists` is asked once per target per hover gesture.
- Listener hygiene: `wirePane` replaces setters and guards its one `addEventHandler` with
  `putIfAbsent`; `watchWindowOf` removes before adding; header decoration is idempotent by property
  keys; the update listener is deregistered in `dispose()`.
- `CwdWatcher` is one shared daemon thread reading `/proc/<pid>/task/*/children`, not
  `ProcessHandle.children()`; 9 samples in 12 s.
- `Settings.save` merges only this process's diff under a file lock through a temp and rename; the
  batch setters (`replaceKeyBindings`, `replaceProfileBlock`, `setProfileStyle`, `forgetProfile`)
  are one save and one broadcast and no-op when unchanged; geometry is written once on `onHiding`.
- The opacity drag defers to drag end; the path fields validate 300 ms off the keystroke; theme
  import parses off the FX thread; `SettingsSync` has a single worker, a 30 s dirty debounce and an
  interval timer that fires only while a window is focused.
- OSC 7/9/52/133 and the kitty modes are intercepted where the emulator reads; payloads are bounded
  at 1 MiB.

## 8. How to repeat the measurements

```bash
# phases, headless, no window on the desktop (totals via dev-run.sh include Maven's time)
MP=$(ls target/deps/*.jar | grep -v -E 'junit|apiguardian|opentest4j|javafx-.*-(mac|win|linux-aarch64)' | tr '\n' ':')
env -u DISPLAY -u WAYLAND_DISPLAY TERMINA_PERF=1 TERMINA_PERF_EXIT=1 TERMINA_CONFIG_DIR=/tmp/perf-config \
  java --module-path "${MP}target/classes" --add-modules com.termina \
  --enable-native-access=javafx.graphics,com.sun.jna -Dprism.order=sw -Dglass.platform=Headless \
  -m com.termina/com.termina.App
```

Add `-XX:FlightRecorderOptions:stackdepth=512 -XX:StartFlightRecording:filename=x.jfr,jdk.ExecutionSample#period=1ms`
for a profile, and read it with `jfr print --stack-depth 400 --events jdk.ExecutionSample x.jfr`
(the default print depth is five frames, which hides everything of ours under JavaFX). For the
burst, add `-Dtermina.capture=/tmp/x.png -Dtermina.captureCommand='seq 1 400000' -Dtermina.captureAfterCommandMs=9000`.
